## Типовые задачи

### 1. Проверить локальные исходники без сборки образа

Входы: текущий HEAD, все локальные изменения, рабочий Python 3 и Bash. Из корня репозитория:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -B -m unittest discover -s tests -v
bash -n build-sd.sh tools/*.sh apps/*/build.sh overlay/vendor/bin/*.sh
python3 -m json.tool obtainium-apps.json >/dev/null
git diff --check
```

Успех: каждая команда завершилась с кодом 0; сохранить команду, число тестов и снимок исходников. Не соединять независимые команды так, чтобы последний успешный exit скрыл предыдущую ошибку. Ошибка: остановить соответствующий этап, разобрать причину, исправление кода согласовать в рамках отдельной задачи. После изменения исходников повторить затронутые проверки.

При аудите прошли 59 тестов исходного рабочего дерева, shell-синтаксис, JSON и whitespace. Затем другой тред добавил тест: итоговый набор надо пересчитать, прежнее число не считать нормой. Это локальная проверка кода, не функциональная проверка прошивки.

### 2. Проверить APK и закрытые входы

Входы: распакованная законно полученная база A12, файлы A9 именно этой платы, APK из записанных источников, прежние ключи в `secrets/`. Не печатать содержимое ключей, пароли или приватный URL архива.

```sh
R="$PWD"
source tools/required-apps.sh
tvbox_require_apks
tools/setup-sdk.sh --check
tools/apkcert.sh dl/apk/ИМЯ_ПАКЕТА.apk
aapt dump badging dl/apk/ИМЯ_ПАКЕТА.apk
```

Успех: все обязательные APK присутствуют, package ID, версия, ABI, SHA-256 и сертификат соответствуют выбранному источнику и ранее установленной подписи. `tvbox_require_apks` проверяет только непустые файлы; сертификат и package ID он не проверяет. Отсутствующий файл или смена подписи блокируют продолжение; восстановить проверенный вход, не генерировать новый ключ. F-Droid может быть источником APK, но магазин не включать в систему; RuStore допустим лишь как источник APK Алисы.

`tools/package-ci-inputs.sh /ПРИВАТНЫЙ_ПУТЬ/inputs.tar.zst` создаёт архив с базой и всеми обязательными APK. Это отдельное действие с записью большого файла; перед запуском проверить состав скрипта, место и права. Архив не публиковать и не коммитить. После изменения APK прежний архив CI и его checksum устаревают; пересоздать архив и отдельно обновить секретные настройки CI.

### 3. Подготовить локальный кандидат

Входы: предыдущие проверки, достаточное место (CI требует ≥18 GB), прежние ключи, версия и `release/notes/<версия>.txt`, результаты горячего применения изменений. Для обычной подготовки используются eMMC и штатный recovery; отдельный SD-образ исключён.

```sh
tools/build-release.sh
```

**Команда разрушает производные данные:** удаляет `build/`, а сборщики приложений пересоздают `obj/gen/out`. При существующем `release/<версия>` она отказывает. До запуска проверить, нет ли там пользовательских изменений или артефактов, которые нужно сохранить; не удалять их автоматически ради прохода команды. Сборка не должна идти одновременно с редактированием её исходников.

Успех: подписанный OTA, чистый eMMC-комплект, метаданные и семь APK созданы для тех же входов. Выходы: `release/updates/emmc/`, `release/<версия>/emmc/`, `release/Panadonik-<версия>-emmc-clean-install.zip`, `release/obtainium/`. Это кандидат; build-script не выполняет весь аппаратный или security gate.

После сборки:

```sh
python3 -I tools/check-image-wifi-secrets.py build/work/system.img build/work/vendor.img
(cd release/updates/emmc && sha256sum --check SHA256SUMS)
python3 -I tools/analyze-release-logs.py /ПУТЬ/К/ЛОГУ --source "сборка кандидата" --output /ПРИВАТНЫЙ_ПУТЬ/build-analysis.md --fail-on-errors
```

Успех: сканер смог прочитать оба финальных ext4 и не нашёл credentials; суммы совпали, подпись прежним сертификатом подтверждена, ошибки лога разобраны. У `tools/mkota.py` есть функция `verify(pkg, cert)`; запуск файла как CLI **собирает и подписывает**, не применять его CLI к готовому OTA как «проверку». Проверку подписи оформить через существующую функцию и доверенный сертификат с фиксацией результата. Не подменять подпись одной checksum. `tools/package-clean-install.sh` проверяет отдельную подпись архива; `docs/install-from-stock.md` описывает её проверку.

Ошибка чтения образа — провал сканирования, не отсутствие секретов. Прежние результаты относятся только к прежнему артефакту. При ошибке не публиковать и не устанавливать кандидат.

### 4. Проверить IPTV

Входы: `tools/iptv-sources.txt`, adult allowlist, предыдущая JSONL-история и согласованный путь результата. Сначала статическая проверка:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -B tools/check-public-release.py --sources tools/iptv-sources.txt
```

Далее сетевые проверки (не запускались этим аудитом):

```sh
python3 -I tools/iptv-merge.py --sources tools/iptv-sources.txt --out /ПРИВАТНЫЙ_ПУТЬ/iptv-candidate.m3u
python3 -I tools/iptv-verify.py /ПРИВАТНЫЙ_ПУТЬ/iptv-candidate.m3u --report /ПРИВАТНЫЙ_ПУТЬ/iptv.csv --history /ПРИВАТНЫЙ_ПУТЬ/история.jsonl --scope global
python3 -I tools/check-public-release.py --sources tools/iptv-sources.txt --playlist /ПРИВАТНЫЙ_ПУТЬ/iptv-candidate.m3u --min-adult 20
```

Успех: сохранены результаты измерений сегментов ≥1080 строк; русские категории, 18+ первой и ≥20 каналов 18+, без детских и дублей; история учтена. M3U, проверенный в CI, должен совпасть по SHA-256 с извлечённым из финального образа. Списки, live-проверка и воспроизведение — разные уровни доказательств.

`--scope device` лишь помечает историю: он не направляет запросы через приставку. Для device-проверки сначала обеспечить и описать реальный путь трафика через неё. `--prune` и `--dedupe-file` могут переписать результат; не применять их к единственной копии истории/исходного списка. Ошибка или недостаток каналов блокируют tagged dev/stable. `--allow-adult-gap` разрешён только для временного non-tag артефакта и только как раскрытый пробел, не для релиза.

### 5. Горячая проверка и аппаратный QA

Входы: конкретная приставка/ревизия, выбранный ADB serial, идентификация установленного ПО и авторизация пользователя для изменений. Безопасный старт — `adb devices -l`, затем адресованные команды чтения, например `adb -s SERIAL shell getprop sys.boot_completed`. Не считать `offline` завершённой загрузкой. При зависшем опросе сначала проверить его процесс/handle и доступность, не перезагружать устройство автоматически из-за таймаута наблюдения.

Горячие правки, перезагрузка, установка и запись разделов не являются частью аудита документов. Для команд через `su` соблюдать родительский AGENTS.md: сложную команду поместить в локальный скрипт, проверить его, передать на устройство и выполнить; не использовать вложенные кавычки с конвейерами для записи блоков. Двоичные снимки писать в файл на устройстве, затем `adb pull` и сверять SHA-256.

В аппаратном прогоне нужны: холодная загрузка до рабочего стола, которым можно управлять с пульта; сеть Wi‑Fi/Ethernet; QR с запуском соответствующей службы; IPTV и торрент-фильм; все кнопки USB-пульта и PAGE в обе стороны; GPU/декодер/плавность и температура; отключённый swap и zRAM; анализ всех новых критических ошибок. Длительность и температурные/кадровые пределы стресс-теста ещё требуют согласования. Не повторять разгон и включение zRAM ради теста: zRAM запрещён.

Сетевой аудит: `python3 -I tools/device-monitor.py --serial SERIAL` даёт ограниченную сводку. Для захвата нужны контролируемая сеть и интерфейс, действительно видящий трафик приставки: `--capture-interface ИНТЕРФЕЙС --controlled-network --capture-seconds 30`. Обычный порт коммутатора компьютера не гарантирует видимость всего трафика приставки. Проверить ограничения удаления секретов/IPv6 и видимость HTTPS; перед публикацией вручную просмотреть очищенную сводку. Сырые журналы и PCAP не коммитить.

Ошибка: сохранить частный сырой материал и очищенную сводку согласно политике хранения, поставить fail/pending, не маскировать источник ошибки фильтром. Для PCAP текущий gate требует `raw_capture_retained=false`; закрывать его только после фактического удаления сырого захвата.

### 6. Gate и подтверждение выпуска

```sh
V=$(sed -n 's/^ro.tvbox.release=//p' build-sd.sh)
OTA="/ПУТЬ/К/ПРОВЕРЕННОМУ/tvbox-update-$V-emmc.zip"
python3 -I tools/check-release-evidence.py --file "docs/release-qa/$V.json" --version "$V" --channel dev --ota "$OTA"
python3 -I tools/check-release-evidence.py --file "docs/release-qa/$V.json" --version "$V" --channel stable --ota "$OTA"
```

Это независимые проверки: фиксировать exit code каждой. Для dev допускаются раскрытые security-риски, но функциональная/сетевая приёмка обязательна; stable требует `security_review=pass`. JSON и MD должны согласовываться, а результаты — относиться к финальному артефакту. Старый `pass` не переносить.

Подготовленный локально workflow по `candidate/**`, schedule и workflow_dispatch создаёт временный кандидат; сборка и QA-артефакты хранятся три дня. Для продвижения в JSON нужны `candidate.actions_run_id` успешного кандидатного запуска, его полный `candidate.source_commit` и `candidate.ota_sha256` принятого OTA. Теговый запуск проверяет происхождение run, отсутствие изменений исходников вне `docs/release-qa/`, скачивает именно этот artifact и сверяет SHA-256 OTA, плейлист и протокол. При истечении срока хранения нужен новый кандидат и новая приёмка; локальный OTA без Actions run этим маршрутом не продвигается. Новый workflow ещё не проверен сквозным запуском в GitHub.

Теги `dev-v<версия>` и `v<версия>` запускают публикацию автоматически. В workflow нет отдельного шага ручного одобрения, поэтому **не отправлять публикационный тег до подтверждения пользователя**. Ночной кандидат не становится релизом из-за успешного CI.

Представить пользователю: артефакт и SHA-256, подпись, исходники/diff, согласованные MD/JSON, фактические тесты, известные риски, описание выпуска и способ установки. Отдельно получить согласие на очистку данных, если она требуется; прошлое согласие не повторно используемое. Завершение и публикация релиза требуют подтверждения пользователя после итоговой приёмки.

6. Восстановить первичную настройку Wi‑Fi WPA2, Алисы/USB-микрофона, Obtainium и проверить сохранение/запросы разрешений в новом образе. Наличие кода настройки и успешный запуск Activity не равны функциональному результату.

## Неоднозначности, которые нельзя закрывать догадкой

- Размер: 700 MB какого артефакта — подписанного OTA, чистого комплекта или разделов, MB или MiB?
- Графический стресс: длительность, допустимая температура, лимит пропусков кадров и воспроизводимый набор нагрузок?
- Регуляторный домен: фактическая страна эксплуатации и реально поддерживаемые firmware коды; исторические US/XZ не являются универсальным разрешением.
- Какие проверки/артефакты готов утвердить пользователь? Пока нет итогового подтверждения, выпуск не завершён.
