# Воспроизводимая оптимизированная сборка для Android TV на RK3318/RK3328 (Android 12): VLC, TorrServer, TV Launcher, Obtainium, Hypatia, LineageOS WebView

**Дата проверки: 2026-11-27.** Все версии, даты релизов, статусы каналов и ссылки приведены по состоянию на этот день. APK не скачивались и не передавались: выводы о подписи, ABI и содержимом APK сделаны по исходникам, сборочным файлам, манифестам, метаданным GitHub API и страницам проектов. Аппаратные замеры не проводились, поэтому ни одно утверждение об ускорении не является подтверждённым.

## Главный вывод

Ни один из шести проектов не предоставляет публично подтверждённой бит-в-бит воспроизводимой сборки, которая совпадала бы с официальным APK. F-Droid-верификация подтверждает отдельные версии TV Launcher, Obtainium (до 1.7.1), APK-обёртки TorrServe и старых сборок Hypatia, но это воспроизводимость в среде F-Droid для конкретных артефактов, а не гарантия совпадения вашей локальной сборки с GitHub-релизом.

Технически собрать пять из шести проектов можно. Практический смысл невелик: официальные релизы уже собраны с релизными флагами, а «оптимизация» через `-O3`, LTO, `abiFilters` или обфускацию либо уже используется, либо не даёт измеренного выигрыша. Для VLC, TorrServer, Obtainium и Hypatia значительная часть нативного кода поставляется предварительно собранной (libVLC AAR, Go-бинарник, Flutter/Cronet, отсутствие native-кода соответственно), поэтому самосборка не пересобирает то, что могло бы ускориться.

Главный блокер — подпись. Самосборный APK подписан другим ключом и не обновляет официальную установку; смена канала требует удаления приложения и потери данных. Для TorrServer серверный бинарник — вообще не APK, а ELF-файл, который клиент TorrServe скачивает и запускает.

LineageOS Chromium WebView стоит особняком: на стоковой приставке Android 12 без root и без изменения системного образа заменить WebView практически невозможно. Провайдер должен быть системным приложением или иметь подпись, объявленную в конфигурации, а на GMS-устройствах разрешены только пакеты `com.google.android.webview*`; к тому же нужна совместимая TrichromeLibrary.

Исходная предпосылка «32-битный userspace при 64-битном ядре» — типичная для RK3318/RK3328, но не универсальная. Её нужно проверить на конкретной приставке командой `getprop ro.product.cpu.abilist`: от этого зависит, нужен ли `armeabi-v7a` или `arm64-v8a` APK.

Официальный APK — отдельный проект [YouROK/TorrServe](https://github.com/YouROK/TorrServe/releases) (`ru.yourok.torrserve`), который после установки скачивает серверный бинарник через «Updates → Update server from network». F-Droid публикует FOSS-вариант APK-клиента, но не сервер.

**Лицензия.** GPL-3.0-only по `LICENSE` и метаданным GitHub API; F-Droid указывает `GPL-3.0-only`. Ключевые зависимости: форк `tsynik/torrent` (MPL-2.0), `go-fuse` (BSD-3-Clause), `bbolt`/`gin`/`quic-go`/`zeroconf` (MIT), `go-arg`/`browser` (BSD-2-Clause). MPL-2.0 совместима с GPLv3 через «Larger Work» §3.3, но исходники MPL-файлов должны оставаться доступными.

**Сборка, ABI, минимальный Android.** Сервер — обычное Go-приложение, `module server`, `go 1.25.7`, точка входа `./cmd`. Релизный CI `.github/workflows/ts_release.yml` для Android использует Go 1.25, NDK и `CGO_ENABLED=1`: `armv7a-linux-androideabi21-clang` для `GOARCH=arm GOARM=7`, `aarch64-linux-android21-clang` для `GOARCH=arm64`. Это даёт минимальный API 21 (Android 5.0). Перед сборкой CI выполняет `go run gen_web.go`: Node.js/Yarn собирают web-UI, который встраивается через `//go:embed`. Локальный `build-all.sh` содержит жёсткий путь `NDK_TOOLCHAIN=/Users/yourok/Projects/AndroidNDK`, то есть это не переносимый рецепт. APK-клиент TorrServe: `minSdkVersion 16` в master/foss, `minSdk 25` в ветке silo; package lines `ru.yourok.torrserve` и `ru.yourok.torrserve.silo` разные и могут стоять одновременно.

**Подпись и обновления.** Серверные ELF-файлы не подписаны в смысле APK. В `MatriX.152` нет `SHA256SUMS.txt`; в релизах `Silo.*` есть `SHA256SUMS.txt`, но это контроль целостности, не воспроизводимость. Для master/foss `signingConfigs` в `app/build.gradle` нет, а workflow `android.yml` только собирает проект; каким ключом подписаны `MatriX.*.Client`, не подтверждено. F-Droid подписывает APK своим ключом. Самосборный APK не обновит официальный; самосборный серверный бинарник можно подложить через «обновление из файла», потому что это не APK.

**Аппаратное декодирование.** TorrServer — стример, а не плеер: README говорит, что ядро функциональности — кэширование торрентов и передача данных по HTTP. Обработчик `/stream` использует `http.ServeContent` с Range-запросами; вызовов MediaCodec, VPU или GPU там нет. `ffprobe` используется для метаданных, не для декодирования. Опциональный GStreamer-путь (`-gst`) предназначен для HLS remux/transcode и собирается только для Windows/Linux/macOS; build-теги `gst` не включают Android. Значит, на Android TV TorrServer не выполняет ни аппаратное декодирование, ни аппаратный транскодинг: он отдаёт исходный поток, а декодирование — задача плеера (ExoPlayer/Media3, VLC и т.п.). Mali-450/T720 — GPU, а не видеодекодер; за HW-декодирование отвечает VPU через MediaCodec/собственные декодеры плеера.

**Телеметрия, службы, разрешения.** В серверном коде нет analytics, Sentry, Crashlytics, Mixpanel или Amplitude. Сетевых функций много: DHT, трекеры, UPnP/NAT-PMP, Local Peer Discovery; список трекеров загружается с зеркал `ngosang/trackerslist`; Bonjour/mDNS включён по умолчанию (`EnableBonjour = true`), DLNA по умолчанию выключен. Веб-сервер по умолчанию слушает все интерфейсы на порту 8090, `--httpauth` выключен — в локальной сети web-UI и API доступны без авторизации, пока пользователь не ограничит `--ip` и не включит авторизацию. Rutor-поиск при включении скачивает индекс по HTTP (`http://releases.yourok.ru/torr/rutor.ls`) каждые ~3 часа. APK TorrServe master содержит Firebase Analytics и Crashlytics, `google-services.json`; разрешения включают `WRITE_SECURE_SETTINGS`, `REQUEST_INSTALL_PACKAGES`, foreground-службы `TorrService`/`NotificationTS`, accessibility-службу `GlobalTorrService`. FOSS-ветка без Firebase; silo-ветка скромнее по разрешениям.

**Безопасные флаги.** `-trimpath` — официальный флаг, убирает абсолютные пути; `-ldflags "-s -w"` — официальный, уменьшает размер и убирает DWARF; `-ldflags "-X server/version.Version=<tag>"` — подставляет версию, которую сравнивает TorrServe при обновлении; `GOARM=7` — официальный для `GOARCH=arm`; `-tags nosqlite` — официальный тег, но в текущем дереве и форке `tsynik/torrent` файлов с `//go:build nosqlite` не найдено, вероятно no-op; `-buildvcs=false` — безопасен при сборке из tar без `.git`. Для Android не заменять официальный `CGO_ENABLED=1` на `0` без тестов: меняется модель линковки и resolver/DNS. `-checklinkname=0` — официальный linker-флаг, но он отключает проверку `//go:linkname`, а не «усиливает безопасность».

**Воспроизводимость.** Официально не заявлена. В пользу частичной детерминированности: `-trimpath`, фиксированный тег версии через `-X`, Go-сборка обычно детерминирована при одинаковых toolchain/флагах/исходниках. F-Droid-верификация подтверждает APK-обёртку версий 176–179, но не серверный бинарник.

**Почему не собирать самому.** В репозитории нет Android-проекта: самосборка даст ELF, который всё равно нужно запускать через TorrServe или shell. Контрольных сумм и аттестаций нет, сравнивать не с чем. Нужны Go 1.25.7, NDK, Node/Yarn, `swag`; `build-all.sh` не переносим. Самосборный APK-клиент получит другую подпись и не обновит официальный. **Аппаратное декодирование.** Не применимо: лаунчер не воспроизводит видео, в коде нет `MediaCodec`, `MediaPlayer`, ExoPlayer. Единственная медиа-функция — wallpaper engine, который скачивает картинки с Wallhaven/Bing/Picsum/Reddit и декодирует их `BitmapFactory.decodeFile` на CPU; по умолчанию выключен. GPU Mali-450 участвует только в обычном рендеринге интерфейса через HWUI; специальных настроек декодирования нет.

**Телеметрия, службы, разрешения.** Аналитики, crash-репортинга и рекламных SDK нет; зависимости — AndroidX, WorkManager (только github-флейвор) и JUnit. Разрешения: `QUERY_ALL_PACKAGES` (список приложений), `INTERNET` (обновления, обои), `REQUEST_INSTALL_PACKAGES` (только github-флейвор; в fdroid удаляется), `KILL_BACKGROUND_PROCESSES` (RAM killer, выключен по умолчанию). `TvHomeOverrideService` — accessibility-служба перехвата кнопки Home, выключена по умолчанию; она видит все нажатия клавиш, хотя обрабатывает только Home. `github`-флейвор добавляет WorkManager 2.9.0 с `PeriodicWorkRequest` раз в 7 дней и смерженными разрешениями `WAKE_LOCK`, `ACCESS_NETWORK_STATE`, `RECEIVE_BOOT_COMPLETED`, `FOREGROUND_SERVICE`.

**Безопасные флаги.** `assembleGithubRelease` или `assembleFdroidRelease` — штатные конфигурации. Оставить R8 full mode, `minifyEnabled`, `shrinkResources`, `proguard-android-optimize.txt`: README прямо предупреждает, что debug-сборки больше и потребляют больше RAM. Не добавлять глобальный `-keep class com.tvlauncher.** { *; }`, не добавлять `abiFilters`/`splits` (native-кода нет), не отключать `shrinkResources`, не менять `applicationId`. Собственный `signingConfig` через `SIGNING_*` безопасен с точки зрения сборки, но меняет идентичность подписи. `--no-daemon`, `org.gradle.parallel=true`, `org.gradle.caching=true` влияют только на машину сборки.

**Воспроизводимость.** F-Droid-верификация для `com.tvlauncher` 1.6.2 (10602) успешна: отчёт `verified: true`, время сборки 2026-10-24 21:11 UTC, differences пусты. Это воспроизводимость F-Droid-сборки `fdroid`-флейвора, а не гарантия совпадения с GitHub-APK. GitHub-репозиторий не содержит `gradle.lockfile`, `verification-metadata.xml`, `distributionSha256Sum`; SDK/build-tools ставятся через `sdkmanager` без пиннинга; `versionCode`/`versionName` подставляются `sed` из тега; ключ подписи — секрет. Поэтому локальная сборка не обязана совпасть с GitHub-APK.

**Почему не собирать самому.** Нет запаса для оптимизации: release уже с R8 full mode и shrink, native-кода нет, ABI-флаги бессмысленны. Самосборка подписывается debug-ключом (если не задан свой) и не обновляет GitHub/F-Droid; ключ CI в секретах. Нет dependency locking и пиннинга toolchain — локальная сборка не воспроизводима. F-Droid уже публикует проверенную воспроизводимую сборку 1.6.2. В 2026 году вышло 8 релизов; F-Droid настроен на автообновление по тегам, самосборку пришлось бы пересобирать вручную.

Базы сигнатур скачиваются и GPG-проверяются отдельно, самосборка их не обновляет и не решает проблему остановившегося генератора. В манифесте нет Leanback-лаунчера, `MainActivity` портретная — сборка не добавляет TV-совместимость. AGPL-3.0 требует выполнения лицензионных обязательств при раздаче. Для аудита достаточно локальной сборки без замены установленного приложения.

## 6. LineageOS Chromium WebView

**Официальный репозиторий и канал.** Исторический монолитный [android_external_chromium-webview](https://github.com/LineageOS/android_external_chromium-webview) заморожен на Chromium **100.0.4896.127** (ARM/ARM64) и 93.0.4577.82 (x86/x86_64), последний коммит 2022-04-07; тегов и GitHub Releases нет. Актуальная поставка разнесена на [patches](https://github.com/LineageOS/android_external_chromium-webview_patches) и четыре prebuilt-репозитория (`_prebuilt_arm`, `_prebuilt_arm64`, `_prebuilt_x86`, `_prebuilt_x86_64`), где APK лежат в Git LFS. На 2026-11-27 версия — **Chromium 158.0.8127.92** (коммиты 2026-11-16/17). Размеры из LFS-указателей: arm 98 976 335 байт, arm64 263 013 311 байт, x86 158 851 487 байт, x86_64 363 897 509 байт. Манифест LineageOS 19.1 (Android 12) подключает `external/chromium-webview/patches` и `prebuilt/*` с `revision="main"`, то есть все актуальные ветки, включая 19.1, получают один и тот же prebuilt WebView с `main`. Репозиторий [LineageOS/android_external_chromium](https://github.com/LineageOS/android_external_chromium) — древний форк CM 9.1.0 (последний push 2018), для современного WebView непригоден. AOSP-альтернатива `platform/external/chromium-webview` в ветке `android12-release` содержит Chromium 91.0.4472.114 (2021), то есть AOSP-образ Android 12 поставляется со старым WebView.

**Лицензия.** Chromium — BSD-3-Clause; в каталоге `third_party` на теге 158 — 337 записей со своими лицензиями (FFmpeg, ICU, libvpx и т.д.), то есть это совокупность лицензий, а не одна BSD. В prebuilt-репозиториях LineageOS файла `LICENSE` нет; `Android.mk`/`os_pickup.mk` содержат стандартный Apache-2.0-заголовок AOSP-шаблона, а `os_pickup.bp` — автогенерированный Soong-модуль с `license_kinds: ["SPDX-license-identifier-Unicode-DFS"]` и комментарием «large-scale-change unable to identify any license_text files». Это артефакт миграции и **не соответствует** реальной лицензии Chromium; считать `Unicode-DFS` лицензией WebView нельзя.

**Сборка, ABI, минимальный Android.** WebView собирается не из репозитория LineageOS, а из `chromium/src` инструментами Chromium: x86-64 Linux, не менее 8 ГБ RAM (рекомендуется >16 ГБ), не менее 100 ГБ диска, `depot_tools`, `fetch android`, `build/install-build-deps.sh`, GN + Siso/Ninja, цель `autoninja -C out/Default system_webview_apk`. LineageOS публикует точный набор GN-аргументов: `target_os="android"`, `is_debug=false`, `is_official_build=true`, `is_chrome_branded=false`, `use_official_google_api_keys=false`, `ffmpeg_branding="Chrome"`, `proprietary_codecs=true`, `enable_resource_allowlist_generation=false`, `enable_remoting=false`, `is_component_build=false`, `symbol_level=0`, `enable_nacl=false`, `blink_symbol_level=0`, `webview_devui_show_icon=false`, `dfmify_dev_ui=false`, `disable_fieldtrial_testing_config=true`, `android_default_version_name="158.0.8127.92"`, `android_default_version_code="8127092$$"` (`$$` — суффикс архитектуры: 00 arm, 50 arm64, 10 x86, 60 x64). `use_thin_lto` включается автоматически при `is_official_build=true` на Android; `symbol_level` по умолчанию 2, LineageOS ставит 0. PGO (`chrome_pgo_phase=2`) включается только при `is_official_build` и `is_high_end_android`, а `is_high_end_android = target_cpu == "arm64" || target_cpu == "x64"`; для 32-битного arm PGO-профиля нет. Для 32-битного arm: `arm_version=7`, `arm_use_neon=true`, `arm_float_abi="softfp"`.

ABI: LineageOS собирает `webview` с `arch: { arm, arm64, x86, x86_64 }`; `arm` — только `armeabi-v7a`; `arm64` — `arm64-v8a` + `armeabi-v7a` (Chromium включает 32-битный код в 64-битную сборку WebView); x86/x86_64 — эмуляторы/планшеты. Документация Chromium: «Any Android device which is able to run 64-bit applications must use a 64-bit build: a WebView built for arm will not function correctly on an arm64 device»; и наоборот, устройства с 64-битным CPU, но 32-битным Android требуют 32-битный WebView. `minSdkVersion` WebView 158 — **29 (Android 10)** (`default_min_sdk_version = 29`), `targetSdkVersion 36`; Android 12 (API 31) подходит, и требование WebView Update Service «targetSdk не ниже SDK платформы» выполнено (36 ≥ 31).

**Подпись, обновления, Trichrome, установка на сток.** В `os_pickup.bp` — `default_dev_cert: true`, в `os_pickup.mk` — `LOCAL_CERTIFICATE := $(DEFAULT_SYSTEM_DEV_CERTIFICATE)`. Soong документирует `default_dev_cert` как «Sign with the default system dev certificate». Официальные сборки LineageOS подписаны приватными ключами LineageOS, поэтому WebView в образе пересобирается/переподписывается ключом ROM (releasekey), а не подписью из LFS-файла. Внутри одной системы обновление WebView возможно только пакетом с тем же именем и подписью: `WebViewFactory.verifyPackageInfo()` бросает `MissingWebViewPackageException("...signature mismatch")`. GitHub-APK из LFS, установленный поверх стокового WebView, подписанного ключом вендора/Google, обновиться «поверх» не сможет; документация Chromium предупреждает, что предустановленный APK нужно удалить, иначе будет signature mismatch.

Провайдером WebView на user-сборке может быть либо системное приложение (предустановленное в `/system` или `/product`), либо обычное приложение, чья подпись заранее объявлена в конфигурации: `WebViewUpdateServiceImpl.providerHasValidSignature()` разрешает системные приложения «regardless of signature», а не-системные — только при совпадении с объявленной подписью. Список провайдеров задаётся в `frameworks/base/core/res/res/xml/config_webview_packages.xml`; в AOSP Android 12 там один провайдер `com.android.webview` с `availableByDefault="true"` и без `<signature>`. На GMS-устройствах допустимые имена — `com.google.android.webview` (по умолчанию), `...beta`, `...dev`, `...canary`; `com.android.webview` разрешён только на userdebug/eng. На GMS-приставке провайдер `com.google.android.webview` зависит от TrichromeLibrary: Trichrome использует отдельные приложения Chrome и WebView и общую библиотеку `libmonochrome.so` в `TrichromeLibrary`; замена одного WebView-APK без соответствующей библиотеки ломает загрузку. Документация Chromium: «Unmodified retail Android devices cannot generally have their WebView replaced or modified for security reasons». Без root нельзя положить APK в `/system`/`/product`; разблокировка загрузчика/отключение verity — отдельная процедура, OTA может откатить изменения. На userdebug/eng проверки подписи/предустановки/versionCode отключены, но это не типичная стоковая приставка.

**Аппаратное декодирование.** Chromium на Android декодирует видео через системный MediaCodec: `media/base/android/media_codec_bridge.h` объявляет мост к `android.media.MediaCodec` с типами `kAny/kSecure/kSoftware`; `media/gpu/android/codec_allocator.cc` создаёт `CodecAllocator` и вызывает `MediaCodec.configure()` с таймаутом 800 мс. WebView использует тот же медиастек, поэтому HW-декодирование — это кодеки, которые предоставляет прошивка через MediaCodec (OMX/CCodec), а не GPU. Для RK3328 есть mainline-binding `rockchip,rk3328-vdec` (в паре с `rk3399-vdec`); для RK3318 отдельного совместимого binding в mainline нет (в списке только rk3288, rk3228/rk3328, rk3399, rk3576, rk3588) — поддержка VPU в вендорском ядре/прошивке RK3318 не подтверждена. На 32-битном userspace нужны 32-битные OMX/CCodec; наличие кодеков проверяется `dumpsys media.codec`/`media_codecs.xml`, а не по SoC. Mali-450 не декодирует видео, только выводит кадры. Итог: HW-декодирование применимо в принципе, но на конкретной приставке требует проверки и замера; гарантировать его нельзя.

**Телеметрия, службы, разрешения.** Манифест WebView 158 объявляет `ACCESS_NETWORK_STATE`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_SPECIAL_USE`, `INTERNET`, `POST_NOTIFICATIONS`, `RECEIVE_BOOT_COMPLETED`. Службы (процессы `:webview_service`/`:webview_apk`): `MetricsBridgeService`, `MetricsUploadService`, `AwMinidumpUploadJobService`, `CrashReceiverService`, `AwVariationsSeedFetcher`, `VariationsSeedServer`, `SafeModeService`, `DeveloperUiService`, `JsSandboxService0`, `AwNetLogService`; провайдеры — `DeveloperModeContentProvider`, `SafeModeContentProvider`, `SafeModeVariationsSeedContentProvider`, `LicenseContentProvider`, `FileProvider` для net-log. UMA-метрики: `AwMetricsServiceClient.setConsentSetting(userConsent)` вызывает `setHaveMetricsConsent(userConsent, !ManifestMetadataUtil.isAppOptedOutFromMetricsCollection())`; отправка включается только если пользователь включил «Usage & diagnostics» в настройках Android и приложение-хозяин не отписалась метаданными `android.webkit.WebView.MetricsOptOut`. Crash reporting: в манифесте есть `AwMinidumpUploadJobService` и `CrashReceiverService` (Crashpad/minidump); конкретные условия выгрузки в LineageOS-сборке не прослежены — не подтверждено. Патчи LineageOS отключают persistent histograms, загрузку variations seed, component updater pings, autofill-коммуникацию и metadata uploads, добавляют флаг отключения внешних intent-запросов; это снижает фоновую сетевую активность, но не отменяет INTERNET.

**Безопасные флаги.** `is_official_build=true` — официальный релизный профиль; AOSP: «Only official builds should be distributed to users, as non-official builds are intended for development and may not be configured appropriately for production». `is_debug=false`, `is_component_build=false` (WebView несовместим с component builds), `symbol_level=0`, `blink_symbol_level=0`, `use_thin_lto=true` (автоматически при official build на Android), `enable_nacl=false`, `disable_fieldtrial_testing_config=true`, `is_chrome_branded=false`, `use_official_google_api_keys=false`, `target_cpu="arm"` для 32-битного userspace, `ffmpeg_branding="Chrome"`, `proprietary_codecs=true` (юридический риск H.264/AAC: AOSP советует получить юридическую консультацию перед распространением). `exclude_unwind_tables=true` не рекомендуется: экономит размер, но ломает стектрейсы. Опасные изменения: ручная правка `targetSdkVersion` без `android_sdk_release` (новые API всё равно упадут в рантайме), смена имени пакета без правки конфигурации ROM, отключение проверок подписи, `is_debug=true`/component build для раздачи.

**Воспроизводимость.** Chromium заявляет детерминированную сборку: «Chromium's build is deterministic. This means that building Chromium at the same revision will produce exactly the same binary in two builds, even if these builds are on different machines, in build directories with different names, or if one build is a clobber build and the other build is an incremental build». Это проектная цель; для Android используется «simple determinism check» (две clobber-сборки по одному пути), часть файлов внесена в `deterministic_build_ignorelist.pyl`. Для LineageOS опубликован только список GN-аргументов; версии тулчейна, PGO-профили, сборочные скрипты и хэши готового APK (кроме LFS `oid sha256` самого файла) не опубликованы. Поэтому бит-в-бит воспроизвести APK LineageOS 158.0.8127.92 по опубликованным данным нельзя подтвердить. LFS-указатель даёт SHA-256 содержимого APK (например, для arm `sha256:e41069f9...`), что позволяет проверить целостность скачанного файла, но не доказывает воспроизводимость сборки.

**Почему не собирать самому.** Для LineageOS ROM: сборка Chromium требует x86-64 Linux, 8 ГБ RAM (16+ рекомендуется), 100 ГБ диска, `depot_tools`, `fetch android`, GN/Siso/Ninja; нужна подпись ключом ROM и разрешение имени пакета в `config_webview_packages.xml`; каждое обновление Chromium нужно пересобирать вручную, а WebView — один из самых атакуемых компонентов, поэтому CVE придётся закрывать самостоятельно. Для стоковой приставки без root: провайдер должен быть системным приложением или иметь объявленную подпись; подпись предустановленного WebView не совпадает; на GMS разрешены только `com.google.android.webview*`; нужна TrichromeLibrary; положить APK в `/system`/`product` без root нельзя. Даже при успешной подмене HW-декодирование не гарантировано: оно зависит от 32-битных OMX-кодеков конкретной прошивки. Документация Chromium прямо говорит, что немодифицированные retail-устройства обычно не позволяют заменить WebView.

## Что проверить на приставке перед выбором APK

Это не новые ветви исследования, а проверка исходной предпосылки «32-битный userspace». Команды только читают свойства и не меняют систему:

```bash
adb shell getprop ro.product.cpu.abi
adb shell getprop ro.product.cpu.abilist
adb shell getprop ro.build.version.sdk
adb shell dumpsys media.codec | grep -iE 'avc|hevc|vp9'
adb shell dumpsys webviewupdate
adb shell pm list packages | grep -i webview
```

Если `ro.product.cpu.abilist` содержит только `armeabi-v7a,armeabi`, нужен 32-битный APK: VLC `armeabi-v7a`, TorrServer `android-arm7`, Obtainium `app-armeabi-v7a-release.apk`, WebView `arm`. Если первым стоит `arm64-v8a`, но userspace 32-битный, установка arm64-APK может завершиться ошибкой; это зависит от прошивки. `dumpsys media.codec` покажет, какие аппаратные кодеки реально объявлены; `dumpsys webviewupdate` — текущий провайдер WebView и допустимые пакеты. Без этих данных любые выводы о совместимости и аппаратном декодировании остаются предпосылкой.

## Ограничения проверки

APK не скачивались и не распаковывались, поэтому отпечатки сертификатов, наличие `lib/<abi>/` и точные разрешения опубликованных APK местами выведены из исходников и метаданных, а не из криптографической проверки файла. Для VLC отпечаток `c8768d…` подтверждён блогом VideoLAN для 3.5.4 и сторонними каталогами для 3.7.1/3.7.2, но не первичной проверкой APK 3.7.2. Для TV Launcher отпечаток GitHub-APK в репозитории не опубликован; утверждение «все GitHub-релизы подписаны одним ключом» основано на комментарии workflow. Для Obtainium подпись файла `.sha256` проверена GPG, но сам APK не скачивался. Для Hypatia отпечаток `1B:00:8D:…:CC` взят из README и индекса IzzyOnDroid, но APK не распаковывался. Для WebView подпись APK в LFS не проверялась; вывод сделан по `default_dev_cert`/`LOCAL_CERTIFICATE`.

Аппаратные замеры не проводились. Утверждения «может быть быстрее», «ожидаемо», «требует замера» — это не обещания производительности. 4K/10-bit HEVC, цветовые искажения, поведение MediaCodec и реальная скорость сканирования Hypatia зависят от конкретной прошивки, драйверов и плеера. Для RK3318 datasheet заявляет H.264 4K30, HEVC Main 4K60, VP9 4K60, но не Main10; для RK3328 документация платы Firefly заявляет 4K 10-bit H.265/H.264. Это разные источники и разные SoC; переносить их выводы на конкретную приставку без `dumpsys media.codec` нельзя.

Статусы F-Droid и релизов могут измениться после 2026-11-27. F-Droid-верификация TV Launcher 1.6.2 (2026-10-24), Obtainium 1.7.1 (2026-11-22), TorrServe APK-обёртки (176–179) и Hypatia 3.14 — это снимок на дату проверки. Версии 1.7.4/1.7.5 Obtainium и 3.18 Hypatia на дату проверки не имели успешной публичной верификации.
